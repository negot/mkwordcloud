# 要件定義書: リアルタイム・ワードクラウド

## 1. 意図の分析

100人規模のワークショップで、参加者がChrome拡張機能から単語・短文を送信し、会場のプロジェクターに映したWebページのワードクラウドがリアルタイムに更新される仕組みを作る。

- 参加者の体験: ルームコードを入力して参加し、テキストを送るだけ(送信専用)。
- 主催者・会場の体験: ルームを作成し、ワードクラウドのページを投影する。必要に応じてリセット・終了する。
- 完成条件: ローカルで動作確認でき、AWSへIaCでデプロイして100人規模で使える。

## 3. 機能要件

### FR1 ルーム管理

- FR1.1 主催者は、ルームを作成できる。作成時に、参加用のルームコードと、主催者用キーが発行される。[desc] [Q4]
- FR1.2 ルームコードは、推測されにくい長さ・文字種で生成する(8文字以上の英数字、紛らわしい文字を除く)。[assumption]
- FR1.3 主催者は、主催者キーを使って、ルームの集計をリセット(全語を0にする)できる。[desc] [Q4]
- FR1.4 主催者は、主催者キーを使って、ルームを終了できる。終了時にそのルームの全データを即時に削除する。[desc] [Q5]
- FR1.5 ルームは、作成から24時間後に自動で削除される。[Q5]
- FR1.6 主催者キーが無い、または誤っている場合、リセット・終了は拒否される。[Q4]

### FR2 Chrome拡張機能(参加者)

- FR2.1 拡張機能は、Manifest V3で作る。[desc]
- FR2.2 参加者は、ルームコードを入力してルームに参加できる。存在しないルームコードでは参加できず、理由が画面に表示される。[desc]
- FR2.3 参加者は、簡易チャットUIにテキスト(単語・短文)を入力して送信できる。送信専用で、他人の発言は表示しない。[desc]
- FR2.4 送信が拒否された場合(文字数超過、レート制限、ルーム終了など)、参加者に理由が表示される。[assumption]
- FR2.5 拡張機能は、ZIPで配布し、デベロッパーモードで読み込んで使う。参加手順をREADMEに記載する。[Q7]
- FR2.6 拡張機能は、直近に参加したルームコードをブラウザ内にのみ保存してよい。個人を特定する情報は保存しない。[assumption]

### FR3 サーバー(受信・集計・配信)

- FR3.1 サーバーは、参加者から受信したテキストを検証し(FR5参照)、語に分割して頻度を集計する。[desc]
- FR3.2 日本語は、形態素解析(kuromoji.js)で単語に分割する。助詞・助動詞・記号・数字などは、品詞で除外する。[desc] [Q2] [Q6]
- FR3.3 英語は、空白と記号で単語に分割し、大文字小文字を統一し、一般的なストップワード(the, is, a など)を除外する。[desc] [Q6]
- FR3.4 日本語と英語が混在した入力も、それぞれの方法で処理できる。[assumption]
- FR3.5 集計が変わるたびに、そのルームの表示ページへ、更新をリアルタイムに配信する(WebSocket)。[desc]
- FR3.6 表示ページが途中から接続した場合、現在の集計全体を最初に受け取れる。[assumption]
- FR3.7 受信テキスト自体は保存せず、語ごとの出現回数のみを保存する。送信者を識別する情報は保存しない。[desc]

### FR4 表示用Webページ(ワードクラウド)

- FR4.1 ブラウザでルームコードを指定して、ワードクラウドを表示できる。表示のために参加者用の操作は不要。[desc]
- FR4.2 出現頻度が高い語ほど大きく表示する。描画には、d3-cloud(SVG)を使う。[desc] [Q3]
- FR4.3 更新を受信したら、ページを再読み込みせずに自動で再描画する。[desc]
- FR4.4 プロジェクター投影を想定し、文字は遠くからでも読めるよう大きく、背景とのコントラストを十分に確保する。日本語フォントで文字化けしない。[desc]
- FR4.5 表示する語数は上位N語(初期値 100)に制限する。[assumption]
- FR4.6 接続が切れた場合は自動で再接続し、再接続後は最新の集計を表示する。[assumption]
- FR4.7 主催者のルーム作成・リセット・終了の操作画面を、表示ページと同じWebアプリ内に用意する。[desc] [Q4]

## 4. 非機能要件

### NFR1 性能・スケール

- NFR1.1 同時接続は約100人(参加者)+表示ページ数台。入力は1人あたり数秒に1回程度を想定する。[desc]
- NFR1.2 送信から表示ページへの反映は、通常時に3秒以内とする(95パーセンタイル)。[assumption]
- NFR1.3 ピーク時(100人が各3秒に1回送信、およそ毎秒33件)でも、入力の取りこぼしや表示の停止が起きない。[desc]

### NFR2 セキュリティ

- NFR2.1 通信はすべてHTTPS/WSS(TLS)とする。[desc] [Q8]
- NFR2.2 ルームコードを知らない者は、ルームに参加も送信もできない。[desc]
- NFR2.3 入力のサニタイズ: サーバーで制御文字とHTML特殊文字を処理し、表示側では文字列をテキストとしてのみ描画する(HTMLとして解釈しない)。XSSが成立しない。[desc]
- NFR2.4 文字数制限: 1回の送信は最大100文字とする。超過分は拒否する。[desc] [assumption]
- NFR2.5 レート制限: 1接続あたり、1秒に1回、かつ1分あたり最大20回までとする。超過は拒否する。API Gatewayのスロットリングも併用する。[desc] [assumption]
- NFR2.6 CORS制限: REST APIは、表示用WebアプリのオリジンとChrome拡張機能のオリジンからのみ許可する。WebSocket接続も、許可したオリジン以外を拒否する。[desc] [Q8]
- NFR2.7 主催者キーは、十分に長いランダム値とし、サーバーにはハッシュのみを保存する。ログに出力しない。[Q4] [assumption]
- NFR2.8 Lambda・DynamoDB等には、最小権限のIAMを割り当てる。[assumption]

### NFR3 プライバシーとデータ保持

- NFR3.1 個人情報を保持しない。IPアドレスや端末識別子を、アプリのデータとして保存しない。[desc]
- NFR3.2 ルームのデータは、主催者の終了時に即時、または作成から24時間後(DynamoDB TTL)に削除される。[desc] [Q5]
- NFR3.3 アプリのログには、入力テキストを出力しない。ログの保持期間は短く(14日以内)設定する。[assumption]

### NFR4 運用・コスト

- NFR4.1 サーバーレス構成とし、常時稼働のサーバーを持たない。サーバー管理・パッチ当ての作業を発生させない。[desc] [Q1]
- NFR4.2 100人規模のワークショップ1回(数時間)の追加費用は、数ドル以内に収まる。[desc] [assumption]
- NFR4.3 最低限の可観測性として、Lambdaのエラー率とAPI Gatewayの接続数・スロットリングをCloudWatchで確認できる。[assumption]

### NFR5 デプロイとIaC

- NFR5.1 AWS CDK(TypeScript)で、すべてのAWSリソースをコードで定義し、1コマンドでデプロイできる。[desc]
- NFR5.2 デプロイの出力(表示ページのURL、WebSocketのURL、REST APIのURL)を、拡張機能と表示ページの設定に反映する手順を用意する。[assumption]
- NFR5.3 リソースを削除する(`cdk destroy`)と、データも含めて残らない。[assumption]

### NFR6 品質・テスト

- NFR6.1 ローカルで動作確認できる。ローカルでは、サーバー処理を単体で起動し、表示ページと拡張機能から接続できる手順を用意する。[desc]
- NFR6.2 要件ごとに1つ以上の自動テストを用意する(単語分割・除外、サニタイズ、文字数制限、レート制限、ルーム管理を優先)。[assumption]
- NFR6.3 100人規模の負荷を模擬する簡易スクリプトで、NFR1を確認する。[desc]

## 5. 受け入れ基準(主要な例)

- FR1.1 / FR2.2: Given 主催者がルームを作成した When 参加者が正しいルームコードを入力する Then 参加でき、送信画面が表示される。Given 存在しないコード When 参加しようとする Then 拒否され、理由が表示される。
- FR3.2: Given 日本語の入力「私は猫が好きです」 When サーバーが処理する Then 「猫」「好き」などの内容語だけが集計され、「は」「が」「です」は集計されない。
- FR3.3: Given 英語の入力「The Cat is cute」 When 処理する Then 「cat」「cute」が集計され、「the」「is」は集計されない。
- FR4.3: Given 表示ページを開いている When 参加者が「猫」を送信する Then 3秒以内に、再読み込みなしで「猫」が表示または拡大される。
- NFR2.3: Given 入力 `<script>alert(1)</script>` When 送信して表示される Then スクリプトは実行されず、文字列として扱われる(または除外される)。
- NFR2.4: Given 101文字の入力 When 送信する Then 拒否され、理由が表示される。境界値の100文字は受け付ける。
- NFR2.5: Given 同一接続から1秒以内に2回送信 When 2回目を送る Then 2回目は拒否される。
- FR1.3 / FR1.6: Given 誤った主催者キー When リセットを要求する Then 拒否され、集計は変わらない。正しいキーなら集計が0になる。
- FR1.4 / NFR3.2: Given 主催者が終了した When そのルームのデータを確認する Then 何も残っていない。

## 6. 制約

- AWSにデプロイする。IaCはAWS CDK(TypeScript)。[desc]
- 拡張機能はChrome Manifest V3。[desc]
- 個人情報を保持しない。[desc]
- 独自ドメインは使わない。AWS標準ドメインを使う。[Q8]

## 7. 仮定

| ID | 仮定 | 理由 |
|----|------|------|
| A1 | ルームの最大同時数は少数(同時に数ルーム以下)。 | 想定は1回のワークショップ。 |
| A2 | 1ルームの参加者上限は、約100人(余裕を見て200接続まで動く構成)。 | 要望は約100人。 |
| A3 | 拡張機能のIDは、デベロッパーモードでの読み込み後に固定するため、manifestの`key`でIDを固定し、CORS許可に使う。 | CORS制限と配布方法の両立のため。 |
| A4 | 表示ページとルーム管理画面は、1つの静的Webアプリ(S3 + CloudFront)にまとめる。 | 構成を単純にするため。 |
| A5 | kuromoji.jsの辞書読み込みによるコールドスタート(1〜2秒)は許容する。 | [Q2]の回答。必要なら予約済み同時実行や定期ウォームアップを検討する。 |
| A6 | 画面の言語は、日本語を基本とし、英語表記は必須としない。 | 想定利用者が日本語話者のため。 |

## 8. 対象外

- 参加者同士のチャット表示、返信、既読など、双方向のチャット機能。
- ユーザー登録・ログイン(Cognito等)。
- ルームごとのNGワード管理。
- Chrome Web Storeでの公開。
- 独自ドメイン、Route 53、WAFの導入。
- 集計結果の長期保存・エクスポート・分析。
- 日本語・英語以外の言語の単語分割。

## 9. 未解決の事項(後続ステージ向け)

- 既存の辞書(kuromoji.js)をLambdaに同梱した場合のパッケージサイズと、コールドスタートの実測。
- WebSocket API の接続管理(接続IDの保存とブロードキャスト方式)の詳細設計。
- 英語のストップワードの具体的な一覧。
- 「レート制限」を、接続単位で数えるか、拡張機能が付与する匿名トークン単位で数えるか。
