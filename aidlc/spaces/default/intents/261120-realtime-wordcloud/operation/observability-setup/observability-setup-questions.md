# 可観測性の設定 質問票

この作業には NFR Design と Infrastructure Design の成果物がありません。そのため、要件(NFR1.2 反映3秒以内、NFR4.3 Lambda のエラー率と API の接続数・スロットリングを CloudWatch で確認できる)、デプロイ済みの CDK の構成、Deployment Execution の結果を根拠にします。

今デプロイされている監視は、2つの Lambda(`WsHandler`、`HttpHandler`)のエラーアラームだけです(1分ごとに1回以上のエラーが3分続くと発報)。通知先は設定されておらず、発報してもコンソールで見るまで気付けません。各質問の先頭の選択肢が推奨案です。

## Q1. [運用担当] アラームの通知はどうしますか?

- A. メール通知を追加する(推奨): SNS トピックを作り、指定のメールアドレスに通知する。アドレスはデプロイ時に `WORDCLOUD_ALERT_EMAIL` で渡し、コードには書かない。初回に確認メールのリンクを押す必要がある。費用はほぼ0円。
- B. 通知なし(今のまま): ワークショップ中に、主催者が CloudWatch のコンソールかダッシュボードを見る。設定は不要だが、気付くのが遅れる。
- C. Slack などのチャットに通知する: AWS Chatbot の設定が別に必要で、手間が増える。
- X. Other (please specify)

[Answer]:B

## Q2. [運用担当] ダッシュボードを作りますか?

- A. CDK で CloudWatch ダッシュボードを1枚作る(推奨): 2つの Lambda のエラー数・実行時間(p95)・同時実行数、WebSocket の接続数とメッセージ数、HTTP API の 4xx/5xx、DynamoDB のスロットリングを1画面に並べる。ワークショップ中に主催者が開いておける。費用は月3ドル程度(1枚目以降。無料枠で3枚まで無料)。
- B. 作らない: 必要なときに CloudWatch のメトリクス画面で個別に見る。
- X. Other (please specify)

[Answer]:A

## Q3. [運用担当] SLO と、遅延の監視はどうしますか?

- A. ワークショップ中だけの目標として記録し、遅延アラームを1つ追加する(推奨): 目標は「ワークショップの開催中(数時間)に、送信の99%が成功し、95%が3秒以内に表示へ反映される」。`WsHandler` の実行時間の p95 が 2秒を超える状態が3分続いたら発報する(3秒の目標より手前で気付くため)。X-Ray による分散トレースは使わない(処理が Lambda 1段のため、ログと実行時間で十分)。
- B. SLO は文書にだけ書き、アラームは追加しない。
- C. 30日間の可用性目標(例: 99.9%)を定めて、エラーバジェットを管理する: 常時運用のサービス向けで、数時間だけ使うこの用途には過剰。
- X. Other (please specify)

[Answer]:B
