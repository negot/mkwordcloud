# デプロイパイプライン 質問票

この作業にはCI Pipelineと Infrastructure Design の成果物がありません。そのため、Code Generation が作った CDK(`infra/`)、`package.json` のスクリプト、Build and Test の結果を根拠に設計します。ワークショップ用の小さなアプリのため、質問は3つに絞ります。各質問の先頭の選択肢が推奨案です。

## Q1. [デプロイ担当] デプロイの流れと承認はどうしますか?

- A. 手動デプロイ・単一環境(推奨): 担当者がワークショップの前に、手元で `npm run build` と `npm test` を実行し、続けて `npm run deploy` を実行する。環境は1つ(本番相当)で、実行した担当者が承認者になる。CI/CD のサービスを立てないので、運用負荷と費用が増えない。数回しか使わないアプリに合う。
- B. 手動デプロイ・2環境(検証用と本番用): 検証用のスタックで確認してから本番用に出す。確認は確実だが、スタックが2つになり、拡張機能のZIPも環境ごとに必要になる。
- C. GitHub Actions や CodePipeline で自動デプロイ: main への反映で自動デプロイする。繰り返し使うなら便利だが、認証設定(OIDCなど)とパイプラインの保守が増える。

## Q2. [デプロイ担当] 反映の方式(段階的な切り替え)はどうしますか?

- A. CloudFormation による一括更新(推奨): `cdk deploy` で全リソースを一度に更新する。Lambda と静的ファイルは即時に切り替わる。利用者がいないワークショップ前に行うため、段階的な切り替えは不要。更新に失敗した場合は、CloudFormation が自動で元に戻す。
- B. Lambda のエイリアスと CodeDeploy でカナリア(10%ずつ)切り替え: 稼働中のサービスには安全だが、設定と費用が増え、この用途には過剰。

## Q3. [デプロイ担当] ロールバックはどうしますか?

- A. 直前の正常なコミット(Gitタグ)を再デプロイする(推奨): デプロイに成功したら `deploy-YYYYMMDD-N` のタグを付ける。問題があれば、そのタグをチェックアウトして `npm run deploy` をやり直す。デプロイ中の失敗は CloudFormation が自動で戻す。データ(DynamoDB)はルームごとに24時間で消える一時データなので、データのロールバックは不要。
- B. 手動で元の版を探して戻す(タグなし): 準備は不要だが、戻す版を探す手間がかかる。
