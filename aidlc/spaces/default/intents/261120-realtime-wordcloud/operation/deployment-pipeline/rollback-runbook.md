# ロールバック手順書

## 前提

- 版の識別は Git のタグ `deploy-YYYYMMDD-N`。スモークテストに成功した版にだけタグを付ける。[Q3]
- DynamoDB のデータは、ルームごとに24時間で消える一時データで、データのロールバックは行わない。

## ロールバックを始める条件

| 条件 | 対応 |
|------|------|
| `cdk deploy` が失敗した | CloudFormation が自動で元に戻す。スタックの状態が `UPDATE_ROLLBACK_COMPLETE` であることを確認し、原因を直してやり直す |
| スモークテストが失敗した | 下の「手順」で直前の正常な版を再デプロイする |
| ワークショップ中に、反映が止まる、またはエラーが続く | 「手順」で戻す。急ぐ場合は、先に「当日の応急対応」を行う |

## 手順(直前の正常な版を再デプロイする)

1. 戻す先のタグを決める: `git tag --list "deploy-*"` で一覧を見て、直前のものを選ぶ。
2. そのタグをチェックアウトする: `git checkout <タグ>`(未コミットの変更があれば、先に退避するか破棄してよいか確認する)。
3. `npm install` の後、`npm test` と `npm run build` が通ることを確認する。
4. `npm run deploy` を実行する。
5. `npm run apply-outputs` で拡張機能ZIPを作り直す(接続先のURLは変わらない)。
6. `deployment-strategy.md` のスモークテストを実行する。
7. 戻した理由と、戻した版を記録する。

## 当日の応急対応

- 表示ページだけが不調: ブラウザを再読み込みする。WebSocket は自動で再接続する。
- ルームの状態がおかしい: 主催者の「リセット」で集計を空にする。解決しなければ、新しいルームを作り、参加者に新しいルームコードを伝える(拡張機能は、コードを入力し直せば参加できる)。
- 送信が拒否され続ける: レート制限の可能性がある。1分待つ。全員が拒否される場合は、API Gateway のスロットリング(WebSocket: 100 req/s、burst 200)に達していないか、CloudWatch で確認する。
- AWS 全体の障害: 復旧を待つ。復旧後は、ルームのデータが残っているか確認し、残っていなければ新しいルームを作る。

## 手順で解決しない場合

- スタックを削除して作り直す: `npx cdk destroy`(データはすべて消える)、続けて `npm run deploy`。ワークショップ前に限る。
- 担当者の連絡先: プロジェクトの README に追記する(この作業ではAWSアカウントの所有者が担当者となる)。

## ロールバックの後

- 原因を記録し、再発を防ぐテストを追加する(原因が分かるまで、問題のあった版にはタグを付けない)。
