# デプロイ戦略

## 戦略

- CloudFormation による一括更新(`cdk deploy`)。Lambda と静的ファイルは即時に切り替わる。[Q2]
- 段階的な切り替え(カナリア、ブルー/グリーン)は行わない。理由: ワークショップの前に、利用者がいない状態でデプロイするため。切り替え中に影響を受ける利用者がいない。[Q2]
- 更新に失敗した場合は、CloudFormation が自動で直前の状態に戻す。[Q2]
- 切り替えの中止条件: スモークテストの失敗(下記)。失敗したら `rollback-runbook.md` に従う。

## 実施のタイミング

- ワークショップの前日までにデプロイし、スモークテストと、数名での実機確認を行う。
- ワークショップの当日は、原則としてデプロイしない。直前に不具合が見つかった場合のみ、再デプロイまたはロールバックを行う。

## スモークテスト(デプロイ直後に必ず実施)

`cdk-outputs.json` の `WebUrl`、`ApiUrl`、`WsUrl` を使う。

1. 表示ページ: ブラウザで `WebUrl` を開き、ホーム画面が表示されること。HTTP で開いた場合は HTTPS に転送されること。
2. ルーム作成: ホームで「ルームを作成」を押し、ルームコードと主催者キーが表示されること。
3. REST の確認(任意のターミナル): `curl -s -o /dev/null -w "%{http_code}" -X POST <ApiUrl>/rooms` が 201 を返すこと。
4. 参加と送信: 拡張機能ZIP(`npm run apply-outputs` で作り直したもの)を Chrome に読み込み、上で作ったルームコードで参加し、「猫が好きです」と「cat dog」を送信する。
5. 反映: 表示ページに、「猫」「好き」「cat」「dog」が3秒以内に表示されること(「が」「です」は表示されない)。
6. 制御: 主催者の「リセット」で表示が空になること。「終了」でルームが終了し、同じコードでの参加が拒否されること。
7. 制限: 101文字の入力が拒否され、1秒以内の連続送信が拒否されること。
8. 監視: CloudWatch で、2つの Lambda のエラーが 0 であること。

すべて成功したら、デプロイ成功とする。1つでも失敗したら、`rollback-runbook.md` に従う。

## 規模の確認(任意・推奨)

- デプロイ後に、`npm run load-test -- --api <ApiUrl> --ws <WsUrl> --clients 100 --duration 30` を実行し、取りこぼしが無く、反映の遅延が3秒以内(95パーセンタイル)であることを確認する。
- 初回の送信で kuromoji の辞書読み込みによるコールドスタート(1〜2秒)が発生する。ワークショップの数分前に、1回ダミーのルームで送信して Lambda を温めておくと、最初の反映が遅れにくい。
- 負荷試験のルームは、終了操作で削除する(24時間後には自動でも削除される)。
