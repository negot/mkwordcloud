# セキュリティ設計

対象: 承認つきデプロイスクリプト。コンポーネントの名前は `logical-components.md` による。

## 認証と権限

- **認証(NFR2.1)**: AWS CLI の IAM Identity Center のプロファイル(`AWS_PROFILE`)を使う。スクリプトは認証情報を自分では読まず、AWS CLI と CDK が一時的な認証を使う。長期のアクセスキーは使わない。
- **権限(NFR2.2)**: 管理者権限を使い、権限は絞らない。この広さを補うため、スクリプトは次の順に動く。
  1. 承認の前は、読み取りだけを行う。事前確認の STS と CloudFormation の読み取り、テンプレートの生成、差分の取得。AWS 上の変更は一つも行わない。
  2. 承認の後に初めて、AWS を変更する `cdk deploy` を実行する。
- **誰が承認したか(NFR1.1)**: 承認ログに、OS の実行ユーザー名に加えて、STS の `get-caller-identity` で得たアカウント ID と呼び出し元の ARN を記録する。

## 承認した内容と、デプロイされる内容の一致(Q1 A)

1. `cdk synth` を一度だけ実行して、テンプレート一式(cloud assembly)を保存先のディレクトリに作る。
2. SynthDiff が、保存先の内容のハッシュ(承認時のハッシュ)を計算する。差分の表示と、リスク検出は、その保存先を対象にする。
3. 承認プロンプトの後、デプロイの前に、AssemblyVerifier がハッシュを計算し直して、承認時のハッシュと照合する。
4. 照合の結果(承認時のハッシュ、現在のハッシュ、一致か不一致か)を、開発者に画面で提示する。一致のときも提示する。
5. 不一致のときは、デプロイせず非ゼロで終了する。結果は `approval` 行に記録する。
6. 承認後の `cdk deploy` は、同じ保存先を渡して実行し、再生成しない。

**ハッシュの計算方法**: 保存先のディレクトリにある通常のファイルをすべて、相対パスの昇順に並べる。各ファイルについて「相対パス、改行、ファイルの内容」を順に SHA-256 に与えて、一つのハッシュにする。CDK 自身が作る一時ファイル(ロック用のファイルなど、`synth.lock` と、`cdk.out` 直下の `.cache` 系)は対象から除く。この除外の一覧は、実装時に CDK のバージョンで確認して、テストで固定する。

## 未コミットの変更(Q2 A)

事前確認(ステップ 1)で、作業ツリーに未コミットの変更(未追跡のファイルを含む)があれば、デプロイせず非ゼロで終了する。さらに、ビルド、型検査、テストの後(ステップ 3)にもう一度確認し、追跡対象のファイルが変わっていたら(自動生成物、lockfile の更新など)、停止して変わったファイルを表示する。コミットのハッシュとデプロイされる内容が、常に一致する。ただし、承認ログのファイルとテンプレートの保存先は git 管理外とし、この確認の対象から除く。

## 承認ログ(Q3 A)

- **フェイルクローズ**: AWS を変更する前に、「開始」の行(`start`)と、承認の判断の行(`approval`)を書く。どちらも書けなければデプロイしない。承認ログ自体に書けないときは、記録を残せないため、理由を画面に表示して非ゼロで終了する(`abort` 行も `end` 行も書けない)。`approval` 行は、承認プロンプトとハッシュの再照合の後、デプロイの直前に書き、承認の判断(承認、拒否)と照合の結果を記録する。デプロイ後の「結果」の行が書けないときは、画面に警告を出し、非ゼロで終了する。
- **内容(NFR2.5)**: 日時(UTC)、実行ユーザー名、STS のアカウント ID と呼び出し元の ARN、コミットのハッシュ、保存先のハッシュ、リージョン、変更の要約、データ消失の警告と回答、承認結果、ハッシュの再照合の結果、デプロイ結果、人による確認の結果。秘密情報、トークン、入力テキストは書かない。行の種類ごとの項目は、`observability-design.md` による。
- **CDK の確認(NFR1.1)**: `cdk deploy` には `--require-approval never` を付けない。CDK の既定の確認(IAM などの権限が広がる変更)は、そのまま残す。権限が広がる変更があれば、CDK が画面で人に尋ねる。人が拒否したときは、デプロイは中止され、`deploy` 行に「CDK の確認で拒否」と記録する。スクリプトの承認プロンプトは、変更内容(差分)の承認であり、CDK の確認は権限の広がりへの追加の確認である。
- **保管(NFR2.4)**: リポジトリ内の git 管理外のファイルとし、`.gitignore` に登録する。保管期間は決めない。テストで、`.gitignore` に載っていることを確認する。
- **形式**: 1 行 1 件の JSON(JSON Lines)。後から機械で読める。

## 入力の検証

- 環境変数(`WORDCLOUD_REGION`、`AWS_PROFILE`)は、使う前に形式を検証する。リージョンは `ap-northeast-1` の形式(小文字、数字、ハイフン)に限る。
- 子プロセス(`aws`、`cdk`)は、引数を配列で渡し、シェルを経由しない。ユーザー入力や環境変数を、シェルの文字列に埋め込まない。
- 確認プロンプトは、あらかじめ決めた回答(`yes`、`no`、`y` など)だけを受け付け、それ以外は「いいえ」と同じに扱う。

## ログと出力

- 子プロセスの出力は、画面に表示する前に、アクセスキー、シークレット、セッショントークンの形式(`AKIA`、`ASIA` で始まる文字列、`aws_secret_access_key`、`aws_session_token`)を伏せ字にする。
- 承認ログと標準出力に、認証情報と入力テキストを残さない。デプロイ後の確認は、データを送信しない(NFR2.6)。

## 脅威と対策

| 脅威 | 対策 | 要件 |
|---|---|---|
| 認証情報の漏えい | 長期の鍵を使わない。出力を伏せ字にする | NFR2.1、NFR2.3 |
| 承認と異なる内容のデプロイ | テンプレートを一度だけ生成し、承認の後にハッシュを照合して、結果を人に提示する | NFR1.1 |
| 未コミットの内容のデプロイ | 事前確認とビルド後の再確認で拒否する | NFR1.1 |
| 承認の証拠がない | `start` 行と `approval` 行の書き込みに失敗したらデプロイしない | NFR1.4、NFR2.4 |
| 誤ったアカウントやリージョン | 事前確認で表示し、人が承認プロンプトで確認する | NFR1.2、FR3.7 |
| コマンドインジェクション | シェルを経由せず、引数を配列で渡す | NFR2.3 |
| データ消失を伴う変更 | 置換、削除を検出し、2 段の確認を経たときだけ進む | FR3.6 |

## ADR: 管理者権限を使う

- **Context**: 手元の一人運用で、CDK のデプロイは IAM、CloudFormation など広い操作を要する。
- **Decision**: 管理者権限を IAM Identity Center の一時的な認証で使う。(Q4 A)
- **Consequences**: 権限が広いので、承認の前は読み取りだけを行う設計で補う。誤操作の影響は大きい。
- **Alternatives Rejected**: このスタックの操作に必要な権限だけを持つ専用ロール。権限の洗い出しの手間が大きく、今回は採用しない。
