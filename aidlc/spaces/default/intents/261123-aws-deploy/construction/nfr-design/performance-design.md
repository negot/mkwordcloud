# 性能設計

対象: 承認つきデプロイスクリプト。アプリ本体の性能は変えない(NFR5.5)。

## 所要時間の扱い(Q5 C)

- NFR3.4(全体 15 分以内)は、守るべき要件ではなく**目安**とする。NFR Requirements の NFR3.4 を、この設計で緩める。以降はこの設計が優先する。
- StepTimer が、各ステップの開始、終了、所要時間を表示する。合計が 15 分を超えたときは、超えたことと、ステップごとの所要時間を表示するだけにする。失敗とはしない。
- 人の確認プロンプトの待ち時間は、所要時間に含めない。

## 待ち時間を短くする工夫

| 対象 | 設計 | 要件 |
|---|---|---|
| 人が待たされる前処理 | 事前確認と差分表示は、AWS を変更しない読み取りだけで構成し、承認プロンプトの前に完了させる。目安は 2 分以内 | NFR3.5 |
| 事前確認 | STS とブートストラップ、スタックの状態の取得は、互いに依存しないので並列に実行する | NFR3.5 |
| ビルド、型検査、テスト | 既存の `npm` のコマンドを順に実行する。並列化はしない(失敗時に原因を追いやすくするため) | FR3.4 |
| テンプレート生成 | 一度だけ生成して保存し、差分表示とデプロイで共有する。再生成しない | Q1 A |

## デプロイ後の自動確認(Q4 A)

- HTTP API の応答と、表示用 Web の取得を確認する。1 回ごとのタイムアウトは 10 秒とする。
- CloudFront の反映待ちで失敗しやすいため、30 秒おきに最大 5 回まで再試行する。失敗したら失敗とする。
- 再試行を含めた最悪の待ち時間は、おおよそ(10 秒 × 6 回 + 30 秒 × 5 回)で 3 分半になる。NFR3.6 の目安(2 分以内)は、再試行がないときの値とし、再試行を含めて 4 分以内を上限の目安とする。[assumption]

## 範囲外

- アプリ本体(Lambda、API Gateway、CloudFront、DynamoDB)の応答時間、処理量、キャッシュ。デプロイで設計を変えないため、現行のまま使う。
