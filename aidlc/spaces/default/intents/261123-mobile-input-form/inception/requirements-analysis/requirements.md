# 要件定義: スマートフォン向け簡易入力フォーム

## Sources
- [desc] Initial description: 「Read ./feature-mobile-form.md and build what it describes」。参照先 `feature-mobile-form.md` の要旨は次のとおり。ブラウザ拡張機能が使えないユーザー、およびスマートフォンから Web アクセスするユーザーのために簡易な入力フォームを開発する。拡張機能と同様にルームコードを入力して参加する。ワードクラウド表示画面の追加開発は不要(スライド投影している管理者が表示するため)。
- [scope] Workflow-selected scope: express
- [assumption] 下記「Assumptions」の A1〜A5
- コードベース調査: `aidlc/spaces/default/codekb/mkwordcloud/` の architecture.md、api-documentation.md、code-structure.md

## 意図の分析
ブラウザ拡張機能を入れられない参加者(主にスマートフォン利用者)も、ワードクラウドに単語を送れるようにする。参加方法は拡張機能と同じ「ルームコードを入力して参加」。表示側は既存のまま使う。サーバーは既存の参加者向け契約(HTTP `GET /rooms/{code}` と WebSocket `role=participant` の `submit`)をそのまま使える見込み。

## 機能要件

- **FR1** ルームコードを入力して参加する
  - **FR1.1** 参加者はスマートフォンのブラウザで入力フォームのページを開き、ルームコードを入力できる。
  - **FR1.2** ルームコードは既存の `normalizeRoomCode` と同じ規則で正規化する(8 文字、使用文字は `ABCDEFGHJKMNPQRSTUVWXYZ23456789`)。
  - **FR1.3** 参加操作時に `GET /rooms/{code}` で存在を確認する。存在しない(404)場合は、ルームが見つからない旨を日本語で表示し、再入力できる。
  - **FR1.4** 表示画面の URL に含まれるルームコード(`?room=CODE` 形式、A2 参照)でフォームを開いた場合は、コード入力済みの状態にする。
- **FR2** 単語(テキスト)を送信する
  - **FR2.1** 参加後、テキスト入力欄と送信ボタンを表示する。
  - **FR2.2** 送信は拡張機能と同じ契約で行う。`role=participant` と `clientId` で WebSocket に接続し、`{"type":"submit","text":...}` を送る。
  - **FR2.3** サーバーから `ack` が返ったら入力欄を空にし、送信できたことを表示する。
  - **FR2.4** サーバーから `error` が返ったら、`ERROR_MESSAGES` の日本語メッセージを表示する(`empty`、`too_long`、`too_fast`、`too_many` など)。
  - **FR2.5** サーバーから `ended` が返ったら、ルームが終了した旨を表示し、送信を無効にする。
  - **FR2.6** 入力の上限は 100 コードポイントとし、超過分は送信前に画面上で知らせる(サーバー側の検証は変更しない)。
- **FR3** 接続の維持と識別
  - **FR3.1** `clientId` は `^[A-Za-z0-9_-]{8,64}$` を満たす値を生成し、`localStorage` に保存して再利用する。
  - **FR3.2** 直前に参加したルームコードを `localStorage` に保存し、次回開いたときの入力初期値にする。
  - **FR3.3** WebSocket が切断された場合は、バックオフ付きで自動再接続する(拡張機能の `backoffDelay` と同等の挙動)。接続状態は画面に表示する。
- **FR4** 配信
  - **FR4.1** フォームは既存の web 配信(S3 + CloudFront、同一オリジン)から静的ファイルとして配信する。
  - **FR4.2** 既存の CSP(`script-src 'self'`)に従い、フォームの JavaScript は外部ファイルとして配信する。
  - **FR4.3** `config.json` の `apiUrl` と `wsUrl` を既存と同じ方法で読み込む。
- **FR5** スマートフォンでの使いやすさ
  - **FR5.1** 画面幅 320px 以上の縦持ちスマートフォンで、横スクロールなしに全要素を操作できる。
  - **FR5.2** 入力欄と送信ボタンのタップ領域は 44×44 CSS px 以上にする。
  - **FR5.3** 文言は日本語で表示する(既存の表示画面、拡張機能と同じ言語)。

## 非機能要件

- **NFR1** サーバー互換性: 既存の HTTP / WebSocket API、CORS 許可 Origin、CSP、スロットル設定を変更せずに動作する。変更が必要と分かった場合は設計段階で報告する。
- **NFR2** セキュリティ: ユーザー入力は `textContent` など安全な方法で DOM に出力し、`innerHTML` へ未エスケープで挿入しない。入力テキストをログや保存に出さない(既存方針に合わせる)。
- **NFR3** ブラウザ互換性: iOS Safari と Android Chrome の、各 OS の直近 2 メジャーバージョンで動作する。
- **NFR4** 軽量さ: フォームの JS と CSS の合計は、圧縮前で 50KB 未満とする。外部ライブラリは追加しない。
- **NFR5** ブラウザ側コードの制約: `@wordcloud/core` はルートを import せず、`/protocol` と `/constants` のサブパスのみを使う(ルートが `node:crypto` を含むため)。
- **NFR6** 検証可能性: FR1〜FR3 の判定ロジック(コード正規化、メッセージ処理、再接続の待ち時間)は、ブラウザ無しで単体テストできる形にする。

## 制約
- 既存のモノレポ構成(npm workspaces、TypeScript)とビルド方式(`scripts/build-web.mjs`)に従う。
- CSP は `script-src 'self'`(インライン JS 不可)、`connect-src` は同リージョンの execute-api のみ。
- サーバー側の制限値(本文 100 コードポイント、最短間隔 1000ms、1 分 20 回、HTTP 20 req/s、WebSocket 100 req/s)は変更しない。

## Assumptions
- **A1** 参加者は匿名で、ニックネームなどの追加入力は不要とする。根拠: 拡張機能も匿名の `clientId` のみで送信している。
- **A2** フォームは既存の表示画面とは別の静的ページ(例: `/join.html`)として置き、表示画面(`main.ts`)は変更しない。根拠: 表示画面の追加開発は不要という指示。ルームコードは `?room=CODE` で受け取る。具体的なパスと構成は設計で確定する。
- **A3** 表示画面にフォームへの QR コードやリンクを出す機能は今回の範囲外とし、管理者が URL(またはルームコード)を口頭やスライドで案内する。根拠: 表示画面の追加開発は不要。
- **A4** 送信できる回数や単語数の制限は、サーバー側の既存ルールに任せる。
- **A5** 動作確認は、ローカル開発サーバー(`local.ts`)と単体テストで行う。AWS へのデプロイは、人が行う操作としてこの作業の範囲外に置く。

## 範囲外
- ワードクラウド表示画面の追加開発(指示による)。
- 表示画面への QR コード・リンク表示(A3)。
- サーバー API、インフラ(CDK)の仕様変更(必要と判明した場合のみ設計で報告)。
- 参加者のログイン、ニックネーム、送信履歴の表示。
- AWS へのデプロイ操作。
